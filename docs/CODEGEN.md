# Original RN Codegen: standalone contract experiment

The pinned **@react-native/codegen 0.87.1** now derives a bounded custom native
contract from original RN TypeScript/Flow specs. This begins GF-26: an app author
can describe props, events, ref commands and TurboModule methods in RN's format,
and inspect the common C++/ViewConfig artifacts generated by upstream tools.

The [fixture specs](../tests/codegen/README.md) declare `CodegenProbe` with sync
methods, a Promise, a result struct and event emitter, and `CodegenBadge` with
primitive defaults, a typed activation event and `focus` command. They produce
**12 artifacts**, a schema and an experimental manifest. The Badge has no
Godot adapter yet; this experiment does not render an external component.

## Run and inspect

After laboratory setup:

```sh
node scripts/codegen.mjs generate --root tests/codegen --library CodegenFixture \
  --native-combination tests/codegen/native-combination.json \
  --out build/codegen-fixture --spec NativeCodegenProbe.ts \
  --spec BadgeNativeComponent.ts
node scripts/codegen.mjs verify --root tests/codegen --library CodegenFixture \
  --native-combination tests/codegen/native-combination.json \
  --out build/codegen-fixture --spec NativeCodegenProbe.ts \
  --spec BadgeNativeComponent.ts
npm run test:codegen
```

`generate` requires a new output directory; `verify` compares existing files
without rewriting them. Inspect `schema.json`, `manifest.json`,
`cpp/CodegenFixtureJSI.h`, the component descriptor/props/events/state/shadow
node files and `viewconfigs/CodegenBadgeNativeViewConfig.js`.
The CLI is currently for platform development. It is not the consumer's Play
build hook, and global Node remains unnecessary for the provisioned basic app.

## What is verified

Parsing and generation use the original RN packages, including common C++
generators and the original ViewConfig generator. The wrapper applies an
explicit experimental schema profile before generation. Valid RN features
outside that profile fail visibly rather than disappearing.

The profile covers core ViewProps inheritance, primitive prop defaults,
direct/bubbling events, primitive command arguments with void results, and
TurboModule methods/events using primitives, objects, aliases, arrays, nullable
values and Promises. General reserved native props/colors, enums, platform
exclusions and Paper/interface-only options remain outside this first slice.

| Manifest input | Meaning |
| --- | --- |
| Sources and schema | Spec paths/bytes, combined schema and their SHA-256 hashes |
| Tool identity | Original Codegen version/integrity/source tree, lockfile, Node and wrapper hashes |
| Generated artifacts | Relative paths, upstream generator names and hashes; verification checks every byte and the whole file set |
| Native combination declaration | Explicit SDK/headers/RN/Hermes/Godot/toolchain/dependency/target identifiers supplied again for verification |
| Claims | `nativeCompiled`, `nativeLoaded`, `runtimeExecuted` and `abiCertified` remain false |

The fixture's native combination has synthetic hashes and `purpose: test-fixture`.
Comparing that declaration detects changes; it does not inspect libraries or
prove that a compiled binary satisfies an ABI. Native packaging and the adapter
handshake must provide actual artifact identity in the next slice.

Tool identity also records the installed `@babel/parser`, `hermes-parser` and
`hermes-estree` package versions, lock integrities and source-tree hashes.
Resolution follows the actual upstream import sites, including nested package
installation. This identifies the parser code used; it is not a certification
of the Node binary or the complete operating-system toolchain.

Checks exercise deterministic generation, source edits/set changes, schema
drift/unsupported fields, collisions, native-combination differences, tool
provenance, modified/missing/extra artifacts, source traversal and preserved
output. Original generators remain unchanged. Generated build artifacts stay
outside Git; the specs, wrapper and negative fixtures are public.

## Compile the generated C++ contract

The macOS arm64 Release build also provides a bounded compilation witness:

```sh
python3 scripts/codegen-native-compile.py --out build/codegen-native-proof
```

Use a new output directory on every run. The runner generates and verifies the
12 artifacts, compiles the five component translation units and instantiates a
concrete `NativeCodegenProbeCxxSpec` with sync methods, a typed Promise and event
emitter. It reuses the existing build's C++20 flags/includes and checks inputs
and generated bytes again after compilation. Logs and failure reports remain
in `build/`; generated files are separate from the object files and harness.

The witness targets macOS arm64 Release with minimum OS 13.0. It does not link
or load a library, run Hermes/Godot, attest the synthetic combination or draw a
Badge. Its report describes compilation separately from the generation
manifest's false runtime/ABI claims. Hosted CI runs the same witness after
native setup; a configured job is not a passing job. CI selects its installed
Node explicitly with `--node`; the default remains the provisioned private Node.
The runner records the selected executable's version and SHA-256. The first
hosted attempt failed before compilation because the private executable was
absent; [the correction](evidence/codegen/ci-node-selection.json) retains that
failure and a separate successful six-unit local rerun. The corrected
[hosted run](https://github.com/journey-studios/godot-fabric/actions/runs/37145700599)
passed all five jobs at commit `5d46bba`; its original Codegen artifact records
**6/6** compiled units with CI Node **22.23.2**, distinct from the declared
addon Node **22.23.3**. [hosted-ci.json](evidence/codegen/hosted-ci.json)
retains the actual compiler/Node identities and bounded compilation claims.

[The executed checkpoint](evidence/codegen/README.md) retains the 20-test and
six-translation-unit results, hashes, target and limitations.

## Next native integration

The renderer currently has a fixed provider/mount/command path for its own
components. Merely adding a generated descriptor is insufficient: an unknown
component would reach assumptions about the core's `ControlProps`. Before an
external component can mount, GF-26 must provide an explicit adapter/factory
registration path and reject incompatible packages before they reach that code.

Then the independent consumer must build/load its own module and component
without editing renderer source. Generated props/defaults and removed values,
typed events, commands through public refs, geometry/reordering and unmount
cleanup need actual native tests. Deleted/remounted refs must not address a
replacement view. Specs also need processing before esbuild removes their
types, plus addon/export integration and per-target binary verification.

This manifest/profile is an experimental implementation detail of approved
D13–D16, not approval of the remaining Architecture 2.0 decisions or completion
of GF-26. [The roadmap](../ROADMAP.md) retains its full acceptance.
